状态：待确认（L1-C）—— 确认前不写流程代码。本批改 browser-extension/background.js（消息带 tid）与 content.js（多卡堆叠），不碰 server / engine。

批次范围

  • 动机：content.js 每页只有一张 HUD 卡（固定单例）。同一标签页里有 2 个被接管任务时，后一个的进度会覆盖前一个，前一个的「完成/失败」终态也会被顶掉——多任务场景下浮层给出错误信息。
  • In：background.js — hud() 消息携带任务 tid（含 track() 初始「排队中」推送）；content.js — 卡片按 tid 管理（Map），多卡纵向堆叠（新卡贴近右下角），终态停留后从 DOM 移除并收缩。
  • Out：弹窗任务管理、轮询改 SSE、服务端任何改动。
  • 环境行为（不入图）：页面跳转/关闭时卡片随文档销毁，background 下一轮照常推送。
  • 兼容性说明：background 与 content script 同属一个扩展、整体更新，不存在新旧版本消息错配——不设兼容分支。

主路径（每任务一条生命周期）

n1 · start
需要展示任务状态
background：track() 初始推送或 pollOnce() 轮询更新（每 1.5s）
↓
n2 · step
组装并投递
消息 {type:"hud", tid, payload} 经 chrome.tabs.sendMessage 发到任务所属 tab；payload 含 phase 与三态字段
↓ 发送失败 → f1（注入兜底）
n3 · decision
content 侧判定
payload 是否有效（含 tid、phase 已知）；该 tid 是否已有卡片
↓ 有效但无卡片 → n4 · 已有卡片 → n5 · 缺 tid / phase 未知 → f2
n4 · step
建卡
在堆叠容器末尾新建（新卡在最下方、贴近右下角）
↓
n5 · step
更新
按 tid 定位既有卡片
↓（n4 / n5 汇合）
n6 · step
渲染
按 phase 渲染：progress 三态（排队/连接/进度，1.2.1 行为保持）；done/error 终态样式
↓
n7 · decision
是否终态
progress → 回 n1 下一轮；done/error → n8
↓ done / error
n8 · end
终态停留后移除
done 6s / error 12s（现状时长）后从 DOM 移除该卡，堆叠自动收缩

出口（既有兜底保持）

f1 · fallback
注入兜底
sendMessage 失败（SW 重启前开的老标签页无 content script）→ ensure() 按需注入 content.js 后重推（现状保持）→ 回 n3

f2 · fallback
防御忽略
payload 缺 tid 或 phase 未知 → 忽略，不建卡

设计取舍（待确认点）

  • 不设数量上限：全部展示、终态自动消失。同页并发任务通常 ≤3；若实际出现 >4 的场景再考虑折叠为「N 个任务进行中」聚合卡（现在不做，避免猜需求）。
  • 新卡插最下：堆叠向上生长，最新任务贴近右下角，时间线自然。
  • 终态停留时长保持现状：done 6s / error 12s；移除 DOM（而非仅隐藏），避免长会话里节点堆积。
  • 单任务视觉不变：卡片样式、三态文案、时长全部沿用 1.2.1。
