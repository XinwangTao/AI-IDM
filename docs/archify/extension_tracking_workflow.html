状态：待确认（L1-C）—— 确认前不写流程代码。本批只改 browser-extension/background.js，不碰 content.js / server.py / engine.py。

批次范围

  • In：background.js — PENDING 跟踪状态写入 chrome.storage.session（n3）；SW 唤醒/重启后恢复并续启轮询（r1→r2）；恢复路径不重复推送初始「排队中」HUD；storage 写入失败降级为内存跟踪（r3）。
  • Out：浮层多任务堆叠、弹窗任务管理、/events 或 SSE 推送、engine/server 任何改动。
  • 动机：MV3 service worker 会被休眠/杀掉重启，重启后内存里的 PENDING 清空；idm-tick 闹钟虽唤醒 worker，但 pollOnce() 见 PENDING 为空直接返回——长下载的完成/失败通知与浮层终态静默丢失。

SW 生命周期（本批新增，紫色）与既有兜底（灰色虚线）

r1 · recovery-entry（本批新增）
SW 唤醒/重启
service worker 休眠、被杀、崩溃或浏览器更新后重新加载；onAlarm(idm-tick) 或任意事件触发
↓
r2 · recovery（本批新增）
恢复跟踪
从 storage.session 读回 PENDING；有未完成任务且无定时器 → 重启轮询（不重复推送初始「排队中」HUD）
→ 有未完成任务且无定时器：回到主路径 n4
→ 无未完成任务：到 n8 结束（仅刷新徽标）

r3 · fallback
降级为内存跟踪
storage.session 写入失败：保持现状行为（重启即丢跟踪），不阻塞主流程 → 回 n4

r4 · fallback
服务不可达重试
/status 拉取失败：保留任务与定时器，下一轮再试（现状行为保持）→ 回 n4

设计取舍（待确认点）

  • 用 chrome.storage.session 而非 local：跟踪属于浏览器会话内的临时状态；浏览器整体重启后未完成任务不恢复跟踪（服务端队列仍会下完，靠网页面板/服务端兜底），避免把「陈旧跟踪」误报完成。若你希望跨浏览器重启也恢复，请指出。
  • 恢复时不重发初始「排队中」HUD，避免休眠唤醒时浮层闪一下。
  • LAST（速度采样）不持久化：恢复后首个采样周期速度显示 0，下一轮即恢复，代价可忽略。
